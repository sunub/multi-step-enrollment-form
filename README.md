## 프로젝트 개요

> 주요 작업 내용에 대한 커밋들은 PR에 포함되어 있습니다 : [PR1](https://github.com/sunub/multi-step-enrollment-form/pull/2),   [PR2](https://github.com/sunub/multi-step-enrollment-form/pull/3),   [PR3](https://github.com/sunub/multi-step-enrollment-form/pull/4),   [PR4](https://github.com/sunub/multi-step-enrollment-form/pull/5),  [PR5](https://github.com/sunub/multi-step-enrollment-form/pull/6)

과제 수행 과정에서 향후 폼의 단계가 추가되거나 조건이 변경되더라도 유연하게 대응할 수 있는 확장성과 데이터 정합성을 보장하는 구조를 설계하는 데 목적을 두었습니다.

과제에서 요구한 필수 기능을 구현함에 있어서 복잡한 다단계 폼에서 가장 빈번하게 발생하는 상태 간섭과 예기치 않은 사용자 이탈로 인한 데이터 유실 문제를 해결하는 데 초점을 맞추었습니다. 나아가 실제 서비스 환경을 가정하여 서버 장애 시의 복구 흐름이나 대용량 데이터 렌더링과 같은 엣지 케이스까지 선제적으로 방어하고자 노력했습니다.

이를 달성하기 위해 구현한 핵심 기술적 가치는 다음과 같습니다.

- **다단계 라우팅:** 선언적 방식의 Funnel 패턴을 도입하여 복잡한 조건부 라우팅 로직을 UI 컴포넌트에서 격리하고, 현재 진행 단계를 URL과 동기화하여 비정상적인 접근을 원천 차단했습니다.

- **원자적 상태 분리와 검증 :** Jotai를 활용해 개인 신청과 단체 신청 등 독립적인 도메인 상태를 원자적으로 격리하여 불필요한 렌더링을 방지했습니다. 또한 스텝 이탈 시점과 전환 시점을 결합한 이중 검증 파이프라인을 구축하여 데이터 무결성을 확보했습니다.

- **사용자 경험(UX) 및 데이터 보호:** 폼 작성 중 실수로 인한 데이터 유실을 막기 위해 커스텀 히스토리 블로커인 `useBlocker` 훅을 구현하고, 세션 스토리지 기반의 상태 동기화를 통해 새로고침이나 뒤로가기 시에도 작성 문맥이 안전하게 유지되도록 설계했습니다.

- **예외 상황 및 API 제약 방어:** 단일 API 명세에서 발생할 수 있는 대용량 강의 데이터 메모리 초과 현상을 방어하기 위해 NDJSON 스트리밍 파싱을 도입했습니다. 또한, Mokcking Server를 활용해 서버 에러를 시뮬레이션하여 장애 상황에서도 시스템이 크래시되지 않고 사용자의 재시도를 안정적으로 유도하도록 구현했습니다.

- **도메인 중심 설계와 테스트 자동화:** pnpm workspace 기반의 모노레포를 구축해 디자인 시스템과 타입을 패키지로 분리하고, Vitest와 Playwright를 활용한 계층적 테스트 환경을 구성하여 복잡한 상태 변화의 안정성을 객관적으로 검증했습니다.

수정된 프로젝트 개요가 현재 코드 베이스의 강점을 충분히 대변하고 있다고 느껴지시나요, 혹은 추가로 더 강조하고 싶은 특정 컴포넌트나 훅이 있으신가요?

## 기술 스택

### 메인 웹 애플리케이션

- **Next.js:** 복잡한 다단계 폼의 라우팅 흐름을 직관적으로 제어하기 위해 App Router의 파일 기반 라우팅 시스템을 채택했습니다. 폼 영역 전체에서 발생하는 잦은 상태 변화와 사용자 상호작용을 즉각적으로 처리하기 위해 클라이언트 컴포넌트 위주로 구성하였으며, Next.js의 내장 라우팅 기능을 활용하여 URL 동기화 기반의 Funnel 패턴을 안정적으로 구현하기 위해 도입했습니다.

- **React :** 사용자의 입력에 따라 동적으로 변하는 복잡한 UI 업데이트를 선언적으로 관리하기 위해 채택했습니다.

- **TypeScript:** 개인 신청과 단체 신청처럼 분기점이 많은 도메인 데이터의 무결성을 엄격하게 보장하기 위해 도입했습니다. `any` 타입을 원천 배제하고 Zod 스키마와 결합하여, 프론트엔드와 API 모의 서버 간의 규격 불일치로 발생할 수 있는 런타임 에러를 컴파일 단계에서 사전에 차단하고 개발 생산성을 높이기 위해 채택했습니다.

- **pnpm Workspaces:** 메인 앱, 디자인 시스템, 모의 서버 등 관심사가 분리된 여러 패키지를 효율적으로 관리하기 위해 채택했습니다. Workspace 설정을 통해 모노레포 환경 내에서 패키지 간의 의존성을 손쉽게 주입하고 연결할 수 있으며, 엄격한 심볼릭 링크 구조를 통해 유령 의존성 문제를 방지하여 가볍고 안정적인 패키지 관리가 가능합니다.

### 전역 상태와 Form 상태 관리

- **Jotai:** 다단계 폼의 복잡한 데이터를 하나의 거대한 객체로 묶을 때 발생하는 렌더링 병목 현상을 방지하기 위해 채택했습니다. 폼의 상태를 강의 정보, 개인 신청, 단체 신청 등 독립된 도메인 단위의 Atom으로 쪼개어 관리하여 리렌더링을 최적화하고, `atomWithStorage`를 통해 세션 스토리지와 연동하여 새로고침 시에도 입력 데이터가 유실되지 않도록 안전하게 축적하는 역할을 수행합니다.

- **React Hook Form:** 최대 10명의 참가자 정보를 동적으로 입력해야 하는 단체 신청 폼 등에서, 사용자의 매 타이핑마다 폼 전체가 리렌더링되는 성능 저하를 막기 위해 비제어 컴포넌트 기반인 이 라이브러리를 채택했습니다. 복잡한 폼 상태의 변화를 효율적으로 감지하면서도 렌더링 성능을 방어하기에 가장 적합하다고 판단했습니다.

- **Zod:** 모노레포 환경에서 프론트엔드와 모의 서버 간의 데이터 검증 규격을 단일 진실 공급원으로 통일시키기 위해 도입했습니다. 단순한 형식 검사뿐만 아니라, 단체 신청 시 '참가자 간 이메일 중복 입력'과 같은 배열 수준의 교차 검증 로직까지 스키마 단위로 선언하여 프론트엔드와 백엔드 양측에서 일관되게 처리하고자 사용했습니다.

### 서버 상태 관리

- **TanStack React Query:** 스트리밍으로 파싱되는 강의 목록 등 서버 데이터를 효율적으로 캐싱하여 불필요한 네트워크 중복 요청을 줄이기 위해 도입했습니다. 특히 네트워크 지연이나 에러 발생 시의 백그라운드 재요청 및 재시도 로직을 유연하게 제어할 수 있어, 이번 과제의 주요 엣지 케이스인 서버 장애 시뮬레이션 환경에서도 안정적인 UX 흐름을 유지하는 데 핵심적으로 활용했습니다.

### 스타일링

- **Vanilla Extract:** 독립된 디자인 시스템 패키지 구축하기 위해 채택한 Zero-runtime CSS-in-JS 솔루션입니다. 런타임 성능 저하 없이 완전한 타입 세이프환경을 제공하여, 사전에 정의된 토큰과 변형 규칙을 강제함으로써 다수 컴포넌트의 시각적 일관성을 유지하고 AI 코드 생성 시에도 스타일 파편화를 방지하는 역할을 합니다.

### 테스트 및 품질 관리

- **Playwright:** 사용자가 다단계 폼을 순차적으로 진행하는 검증을 이외에도 브라우저 뒤로가기/새로고침 시의 상태 유지와 강제로 발생시킨 서버 에러(정원 초과, 중복 신청) 상황에서 시스템이 데이터를 보존하고 안전하게 복구되는지를 실제 유저의 브라우저 환경과 동일하게 통합 검증하기 위해 도입했습니다.

- **Vitest & React Testing Library:** 브라우저 환경의 무거운 통합 테스트 대신, 도메인 비즈니스 로직, Zod 유효성 검증 스키마, 그리고 자체 구현한 `useFunnel` 훅의 상태 전환 로직을 빠르고 반복적으로 검증하기 위해 가벼운 테스트 러너로 채택했습니다.

- **Biome:** 여러 패키지로 나뉜 모노레포 환경 전체에서 단일화된 코드 스타일과 품질 기준을 유지하기 위해 도입했습니다. 기존 도구들 대비 압도적으로 빠른 속도로 포맷팅과 린트를 동시에 수행하여 개발 생산성을 높여줍니다.

## 실행 방법

```bash
pnpm install # 패키지 설치 이후
pnpm run dev # dev 명령어를 수행하면 mocking 서버와 next 개발 서버가 동시에 구동이 됩니다.
pnpm run dev:mock # mocking server 만 구동시키기 위해서는 이 명령어를 사용하시면 됩니다.
```

기본값으로 설정되어 있는 Port 에 대한 정보는 다음과 같습니다.

- Next.js 앱: `http://localhost:3000`
- Mock API 서버: `http://127.0.0.1:3101`

### Mock 수강신청 에러 시나리오 제어

mock 서버는  `.env` 에서 환경 설정을 이용하여 에러 상황에 대한 예외 케이스 테스트가 가능합니다. Mocking 서버에서 지원하는 환경 설정들은 아래과 같습니다.

| 설정                            | 동작                                           |
| ----------------------------- | -------------------------------------------- |
| `MOCK_ENROLLMENT_SCENARIO=0`  | `POST /api/enrollments` 정상 응답                |
| `MOCK_ENROLLMENT_SCENARIO=1`  | `POST /api/enrollments`에서 `INVALID_INPUT` 강제 |
| `MOCK_ENROLLMENT_SCENARIO=2`  | `POST /api/enrollments`에서 `COURSE_FULL` 강제   |
| `RANDOM_ERROR_PERCENTAGE=0`   | `GET /api/courses` 랜덤 실패 없음                  |
| `RANDOM_ERROR_PERCENTAGE=100` | `GET /api/courses`가 항상 `SERVER_ERROR`        |

```plaintext
# [유저1=성공, 유저2=정원초과, 유저3=중복신청] 시나리오를 따르고 있습니다.
MOCK_ENROLLMENT_SCENARIO=0

# 랜덤으로 에러가 발생할 확률을 0~100%로 설정이 가능합니다.
RANDOM_ERROR_PERCENTAGE=0
```

테스트를 원하는 상황에 맞춰 `.env`을 설정할 경우 특정 에러 상황에서 적절하게 대처하고 있는지에 대해서 손쉽게 테스트를 수행할 수 있습니다.

#### 주의사항

- `MOCK_ENROLLMENT_SCENARIO`는 `0`, `1`, `2`만 허용합니다.
- `RANDOM_ERROR_PERCENTAGE`는 `0`에서 `100` 사이 숫자만 허용합니다.
- 다른 값을 넣으면 mock 서버는 `500 SERVER_ERROR`를 반환합니다.
- `RANDOM_ERROR_PERCENTAGE`는 `src/components/CourseSelectionStep/CourseSelectionStep.tsx`가 사용하는 `GET /api/courses`에만 적용됩니다.
- `RANDOM_ERROR_PERCENTAGE`로 실패가 발생하면 응답은 `500 SERVER_ERROR`입니다.

## 프로젝트 구조 설명

본 프로젝트는 복잡한 다단계 폼 흐름을 안정적으로 제어하고, 도메인 로직과 UI 계층을 격리하기 위해 pnpm workspaces 기반의 모노레포 아키텍처와 URL 상태 동기화 방식의 Funnel 패턴을 도입했습니다. 우선 모노레포 구조부터 설명하겠습니다.

### 1. Funnel 패턴 설계

저는 이번 과제의 목적인 사용자가 단계별로 Form 채워나가는 방식이 설문조사 패턴에 해당한다고 판단하였습니다. 그래서 이와 관련하여 토스에서 이러한 설문조사 패턴을 해결하기 위한 방향으로 기술 발표를 한적이 있었던 Funnel 이 떠올라 차용하여 적용하였습니다. 각각의 페이지를 하나의 Funeel 로 정의하였고 해당 Funnel 은 다음과 같은 속성을 갖습니다.

```js
// app/courses/funnelConfig.ts
export interface StepConfig<T> {
  id: string;
  name?: string;
  shouldRender?: (state: T) => boolean;
}

export const steps: StepConfig<CoursesFunnelState>[] = [
  {
    id: "course-selection",
    shouldRender: () => true, // 첫 페이지는 무조건 참여할 수 있게끔 합니다.
  },
  {
    id: "individual-member-registration",
    name: "personal",
    shouldRender: canAccessIndividualMemberRegistration,
  },
  {
    id: "group-member-registration",
    name: "group",
    shouldRender: canAccessGroupMemberRegistration,
  },
  {
    id: "review",
    shouldRender: canAccessReview,
  }
];
```

다단계 폼의 흐름을 제어하기 위해 선언적 기반의 Funnel 패턴을 자체 구현하여 적용했습니다. 이를 통해 컴포넌트 내부의 복잡한 조건부 렌더링을 제거하고, 라우팅과 폼 상태 검증을 하나의 파이프라인으로 통합했습니다.

앞선 설정을 사용하기 위해 추상화된 API 를 제공하기 위해 `useFunnel` 훅을 구현하였습니다. 다음 스텝의 ID를 내부적으로 계산하여 `next()`, `prev()` 단방향 액션 함수와 전체 진행률, 첫 스텝 여부, 마지막 스텝 여부 등의 파생 상태를 훅 내부에서 모두 계산하여 반환하므로, 컴포넌트는 오직 View 렌더링에만 집중할 수 있게 되어 결합도가 크게 낮아졌습니다.

다음 스텝의 ID를 내부적으로 계산하여 `next()`, `prev()`와 같은 단방향 액션 함수와 전체 진행률, 첫 스텝 여부, 마지막 스텝 여부 등의 상태를 훅 내부에서 모두 계산하여 반환하므로, 컴포넌트는 오직 뷰 렌더링에만 집중할 수 있게 되어 결합도가 크게 낮아졌습니다.

```tsx
// app/courses/page.tsx (사용 예시)
function EnrollmentFunnel() {
  const funnel = useFunnel<CoursesFunnelState>(steps, funnelState);
  return (
    <Box>
      {currentStep?.id === "course-selection" && (
        <CourseSelectionStep onNext={funnel.next} />
      )}
      {currentStep?.id === "group-member-registration" && (
        <GroupRegistrationStep onNext={funnel.next} onPrev={funnel.prev} />
      )}
    </Box>
  );
}
```

`useFunnel` 훅을 사용하여 단순히 정해진 순서대로 페이지를 이동하는 것이 아니라, 사용자의 입력 상태에 따라 거쳐야 할 스텝이 동적으로 결정됩니다. 예를 들어 사용자가 "개인 신청" 을 선택하면 "단체 정보 입력" 스텝은 활성 스텝에서 완전히 배제되며, 이후 `funnel.next()` 호출 시 개인 신청 다음 단계로 건너뜁니다. 이를 통해 조건부 라우팅 분기 로직을 컴포넌트에서 제거했습니다.

**`packages/@shared/mock`:**  Express를 기반으로 구축한 API Mocking 서버 패키지입니다. 브라우저 레벨의 모킹 도구인 MSW 대신 별도의 Express 서버를 구축한 이유는 테스트의 안정성과 확장성 때문입니다. 제품의 완성도를 높이기 위해서는 E2E 테스트를 통한 사용자 시나리오 검증이 필수적인데, 이 과정에서 MSW를 활용할 경우 브라우저 환경에 따른 제약이 존재했습니다. 모노레포 내에 독립적인 모킹 패키지를 구성함으로써, 프론트엔드 애플리케이션의 구동 환경과 완전히 분리된 상태에서 일관된 API 응답을 제공하며 안정적인 테스트를 수행할 수 있도록 구축했습니다.

**`packages/@shared/types`:** TypeScript와 Zod를 활용하여 구축한 공통 타입 및 스키마 패키지입니다. 프론트엔드 도메인 로직에 종속된 타입과 분리하여, API 요청 및 응답 규격에 사용되는 핵심 타입들을 한 곳으로 모아 관리했습니다. 모노레포 환경에서 이를 별도 패키지로 분리하면, 프론트엔드 앱과 서버가 동일한 스키마를 참조하게 되어 타입 안정성을 보장하고 SSOT을 확립하여 데이터 정합성과 재사용성을 높이고자 하였습니다.

### 3. 상태 관리 및 데이터 파이프라인 설계

다단계 폼의 상태를 관리하기 위해 중앙 집중식 스토어 방식 대신, Jotai를 활용한 원자적 상태 관리 패턴을 채택했습니다. 수강 신청 폼은 크게 '공통 강의 선택 정보', '개인 신청 정보', '단체 신청 정보'라는 세 가지의 독립적인 도메인으로 나뉩니다.

이를 하나의 거대한 단일 객체로 관리할 경우 구조를 한눈에 파악하기 쉽다는 장점이 있지만, 트리의 깊이가 깊어져 상태 업데이트가 번거로워지고, 특정 필드의 작은 변경 예를들어, 단체 참가자 이름 한 글자 수정이 폼 전체의 불필요한 리렌더링을 유발할 수 있다는 구조적 단점이 존재한다고 판단했습니다.

이러한 문제를 방지하기 위해 폼의 상태를 3개의 독립된 Atom으로 분리하여 관리하는 결정을 내렸습니다. 상태를 물리적으로 격리함으로써, 각 스텝의 UI 컴포넌트는 자신이 구독하고 있는 Atom의 변화에만 반응하게 됩니다. 분리된 세 개의 상태는 폼 작성 과정에서는 독립적으로 동작하다가, 마지막 확인 단계와 최종 서버 제출 시점에만 하나로 수집되어 완전한 형태의 페이로드로 조립되도록 데이터 파이프라인을 구성했습니다.

마지막으로, 사용자의 예기치 않은 이탈이나 브라우저 새로고침 시 데이터가 유실되는 경험을 방지하기 위해 Jotai의 `atomWithStorage` 유틸리티를 적용했습니다. 세 개의 아톰은 각각 브라우저의 `sessionStorage`와 실시간으로 동기화되도록 설정하여, 별도의 수동 저장 로직 없이도 해당 브라우저 탭 세션이 유지되는 한 사용자의 작성 문맥이 유지되도록 상태 관리의 안정성을 높였습니다.

### 4. URL 동기화 기반 설계

현재 진행 단계를 Local State가 아닌 URL의 Query Parameter 와 동기화되도록 설계했습니다. 새로고침이나 뒤로가기/앞으로가기 내비게이션 사용 시에도 URL을 기반으로 현재 스텝을 완벽히 복원하여 UX를 개선하고자 하였습니다.

사용자가 임의로 URL 파라미터를 조작하여 접근 권한이 없는 스텝, 예를들어 "리뷰 단계"로 진입을 시도할 경우, `funnelConfig`을 참조하여 사용하는 `useFunnel` 훅 내부의 `currentIndex === -1` 평가 로직이 이를 즉시 감지하고 접근 가능한 최초 스텝으로 자동 리다이렉트시킵니다.

## 요구사항 해석 및 가정

### 폼 아키텍처 및 시스템 구조에 대한 해석과 결정

이번 과제는 단순히 세 단계의 폼을 구현하는 것을 넘어, 향후 단계가 추가되거나 변경될 수 있는 확장성을 고려해야 한다고 생각했습니다. 이를 위해 각 단계의 렌더링 로직을 컴포넌트 내부에 고정하기보다는, `funeelConfig`라는 설정 파일을 통해 관리되도록 구조를 분리했습니다. 이 파일이 폼의 현재 상태를 바탕으로 진입 가능 여부와 유효성 검사 스키마를 결정하게 하여 구조적 유연성을 높이고자 했습니다. 또한, 클라이언트와 모의 서버 간의 유효성 검증을 일관되게 유지하기 위해 모노레포 환경을 구성했습니다. 공용 타입 패키지에 Zod 스키마를 두고 프론트엔드와 백엔드가 이를 공통으로 참조하게 함으로써 데이터 정합성을 맞추고자 노력했습니다.

## 1단계 강의 선택에 대한 해석과 결정

1단계 강의 선택 과정에서는 실제 서비스 환경처럼 데이터가 많을 경우를 가정했습니다. 한 화면에 모든 리스트를 보여주기보다는 페이지네이션을 통해 탐색하는 것이 사용자에게 더 나은 경험이 될 것이라 판단했습니다. 주어진 API가 페이지네이션 파라미터를 지원하지 않는 제약이 있었기 때문에, 프론트엔드에서 NDJSON 기반의 스트리밍 파싱을 도입해 데이터를 지연 평가 방식으로 읽어 들이며 클라이언트 사이드 페이지네이션을 구현했습니다. 아울러 사용자가 많은 강의 중 하나를 선택했을 때 자신의 선택을 쉽게 인지할 수 있도록, 선택한 강의 정보와 결제 금액을 화면 하단에 고정하여 탐색 중에도 지속적으로 확인이 가능하게 화면을 구성했습니다.

### 2-1단계: 그룹 기본 정보 및 인원수 입력에 대한 해석과 결정

단체 신청의 첫 관문인 2-1단계에서는 대표자 정보, 단체명, 그리고 신청 인원수(2~10명)를 입력받습니다. 여기서 폼 설계의 핵심이 되는 요소는 "신청 인원수"라고 보았습니다. 이 숫자에 따라 이어지는 단계에서 렌더링해야 할 참가자 슬롯의 개수가 동적으로 결정되기 때문입니다.

이를 처리하기 위해 인원수 입력 필드의 상태와 참가자 정보 배열의 상태를 유기적으로 연결하도록 설계했습니다. 사용자가 인원수를 변경할 때마다 폼 데이터 내의 참가자 명단 배열 크기가 동적으로 조절되도록 하되, 인원을 늘리거나 줄이는 과정에서 이미 입력해 둔 참가자 데이터가 불필요하게 유실되지 않도록 상태 관리 로직에 주의를 기울였습니다. 더불어 대표자의 이메일과 연락처는 이후 그룹 전체의 주요 소통 창구가 되므로, Zod 스키마를 통해 엄격하게 형식을 검증하여 초기 데이터의 신뢰성을 확보하는 데 초점을 맞추었습니다.

### 2-2단계: 참가자 상세 정보 입력에 대한 해석과 결정

2-2단계는 앞서 설정한 인원수만큼 개별 참가자들의 이름과 이메일을 입력하는 과정입니다. 최대 10명 분량의 데이터를 반복해서 입력해야 하므로, 전체 폼 화면 중에서 사용자 피로도와 입력 실수 발생 확률이 가장 높은 구간이라 생각했습니다.

우선 시각적인 피로도와 모바일 환경에서의 스크롤 압박을 줄이기 위해, 입력 필드를 세로로 길게 나열하는 대신 슬롯을 가로로 넘겨볼 수 있는 카드 형태의 UI를 적용해 보았습니다. 아직 입력하지 않은 빈 슬롯은 시각적인 박스로 표시해 사용자가 남은 입력량을 직관적으로 파악할 수 있도록 구성했습니다.

데이터 검증 측면에서는 개별 이메일 형식 검사를 넘어, 폼에 입력된 참가자들 사이에서 "이메일이 중복으로 입력되는" 상황을 방지하기 위해 배열 수준의 교차 검증 로직을 추가했습니다. 중복이나 형식 오류가 발견되었을 때는 전체 폼의 하단에 경고를 띄우기보다, 문제가 발생한 특정 참가자 슬롯에만 붉은색 테두리와 안내 텍스트를 표시해 문제 위치를 즉시 파악할 수 있도록 했습니다. 이러한 피드백은 사용자가 입력을 마치고 필드를 벗어나는Blur 시점에 제공되도록 하여, 최종 제출 버튼을 누르기 전에 자연스럽게 실수를 인지하고 수정할 수 있도록 유도했습니다.

### 데이터 정합성 유지 및 예외 상황 처리

다단계 폼의 데이터 정합성을 유지하고 예외 상황을 방어하기 위해 다음과 같은 검증 구조와 안전장치를 구현했습니다.

첫째, 유효성 검증은 '개별 필드 이탈 시'와 '스텝 전환 시'를 결합한 이중 검증 파이프라인으로 구축했습니다. 입력 중에는 포커스가 필드를 벗어나는 시점에만 검증을 수행하여 잦은 상태 동기화로 인한 연산 비용과 리렌더링을 최소화했습니다. 이후 사용자가 다음 단계 진입을 시도할 때, Zod 스키마를 통해 해당 스텝의 전체 데이터를 다시 한번 강제로 검증하여 데이터 누락이나 비동기화 상태로 단계가 넘어가는 것을 원천 차단했습니다.

둘째, 조건부 필드 전환 시 발생할 수 있는 잉여 데이터 오염을 방지했습니다. 단체 신청 작성 중 개인 신청으로 유형을 변경할 경우, 사용자에게 확인 대화상자를 노출하고 동의 시 활성화되지 않은 반대편 도메인의 데이터를 즉시 초기화하는 교차 초기화 로직을 적용했습니다.

셋째, 사용자의 실수나 서버 장애로 인한 데이터 유실을 막는 복구 메커니즘을 구축했습니다. 브라우저 뒤로가기나 새로고침에 대비해 현재 진행 단계는 URL 파라미터와 동기화하고, 입력 데이터는 Jotai를 활용해 세션 스토리지에 영속화했습니다. 여기에 `useBlocker` 커스텀 훅을 결합해 예기치 않은 페이지 이탈을 인터셉트하도록 처리했습니다. 또한, 정원 초과나 중복 신청과 같은 서버 에러 발생 시에도 사용자의 폼 데이터가 그대로 보존되도록 구현하였으며, 이러한 예외 복구 과정은 환경 변수로 강제 에러를 발생시키는 E2E 테스트를 통해 안정적으로 동작함을 검증했습니다.

## 설계 결정과 이유

### 1. 폼 상태 관리: 단일 전역 상태 vs 원자적 상태 관리

다단계 폼의 데이터를 관리하는 방식을 결정할 때, 초기에는 React의 내장 Context API나 Reducer를 활용하여 하나의 거대한 객체로 단일 전역 상태를 관리하는 접근을 고려했습니다. 하지만 폼의 입력 필드가 점차 많아지는 상황에서 이 방식을 적용할 경우, 상위 상태 값이 변경될 때마다 하위 컴포넌트 전체가 불필요하게 리렌더링되는 폭포수(현상이 발생할 우려가 컸습니다.

특히 이번 프로젝트처럼 **"개인 신청"** 과 **"단체 신청"** 이라는 구조가 완전히 다른 도메인 데이터가 공존하는 경우, 이를 하나의 거대한 상태 객체로 묶는 것은 오히려 폼의 복잡도만 높인다고 판단했습니다. 이러한 렌더링 비효율성과 구조적 복잡도를 피하기 위해, 최종적으로 Jotai를 활용한 Atomic 상태 관리를 채택했습니다. 전체 폼 데이터를 세 개의 독립된 Atom으로 쪼개어 관리함으로써, 사용자가 단체 신청의 특정 필드를 수정하더라도 개인 신청이나 공통 강의 정보 컴포넌트 등은 전혀 렌더링의 영향을 받지 않는 최적화된 아키텍처를 달성할 수 있었습니다.

### **2. 유효성 검증시점: 제출 시 일괄 검증 vs. 스텝별/필드별 검증**

각 입력 필드의 유효성 검증을 어느 시점에 실행할 것인가에 대해 깊은 고민이 있었습니다. 사용자가 값을 **"입력할 때마다 실시간으로 검증하는 방식"** 은 즉각적인 피드백을 줄 수 있지만, 매 타이핑마다 상태 동기화와 스키마 연산이 실행되어 불필요한 리렌더링과 과도한 연산 비용을 야기할 수 있다고 보았습니다.

반면 **"포커스가 필드를 벗어날 때만 검증하는 방식"** 은 연산 부담을 줄일 수 있으나, 사용자가 값을 채우지 않은 상태에서 포커스를 이동하지 않고 곧바로 다음 스텝 버튼을 누르는 등 예기치 못한 동작을 수행했을 때 검증이나 데이터 동기화가 일시적으로 누락될 수 있다는 한계가 존재했습니다.

이러한 두 방식의 장단점과 엣지 케이스를 비교 분석한 끝에, 평상시에는 포커스를 벗어나는 시점에 검증을 수행하여 연산 효율성을 챙기되 사용자가 다음 단계로 진입을 시도할 때는 폼 전체의 데이터 상태를 다시 한번 검증 파이프라인에 태워 강제로 확인하도록 설계했습니다. 이를 통해 입력 누락이나 비동기화 상태로 다음 단계에 진입하는 오류를 방지하고자 했습니다.

### 3. 스텝 간 상태 유지: 최상위 State vs. URL Query Parameter

다단계 폼에서 각 스텝의 이동 상태를 관리하는 방식을 결정할 때, 초기에는 최상위 레이아웃 컴포넌트에서 `useState`를 사용하여 현재 단계를 추적하는 가장 직관적인 접근을 고려했습니다.

하지만 단순히 컴포넌트 상태에만 의존하는 라우팅은 사용자가 브라우저의 뒤로가기 버튼을 누르거나 페이지를 새로고침할 때 진행 상황이 즉시 초기화되어 첫 페이지로 이탈하게 만드는 한계가 있었습니다. 복잡한 수강 신청 흐름에서는 사용자가 입력 중이던 진행 맥락을 잃지 않도록 보호하는 것이 무엇보다 중요하다고 판단했습니다.

이러한 유실 가능성을 방지하기 위해, 현재 진행 스텝 상태를 브라우저 URL의 Query Parameter(`?step=...`)에 온전히 의존하도록 설계했습니다. 이를 통해 브라우저의 기본 네비게이션(History API)과 다단계 폼의 진행 단계를 매끄럽게 동기화하여, 새로고침이나 뒤로가기 상황에서도 사용자의 흐름이 중단되지 않는 안정적인 라우팅 환경을 구성할 수 있었습니다.

## 미구현 / 제약사항

### 제약사항

```plaintext
GET /api/courses
```

과제 요구사항에 명시된 강의 목록 조회 API(`GET /api/courses`)는 Offset 이나 Cursor 기반의 페이지네이션 쿼리 파라미터를 지원하지 않는 단일 엔드포인트였습니다. 데이터가 수만~수십만 개로 늘어날 경우, 단일 API 호출로 모든 데이터를 한 번에 로드하면 브라우저 메모리 초과 및 렌더링 지연이 발생할 위험이 있었습니다. 하지만 백엔드와의 API 명세 계약을 임의로 변경할 수 없다는 전제하에 프론트엔드 단에서의 최적화 방법을 모색해야 했습니다.

이 문제를 완화하기 위해 Mocking Server 에서의 데이터 응답 타입을  **NDJSON** 과 `AsyncIterable` 기반의 스트리밍 파싱 방식을 도입했습니다. 데이터를 한 번에 메모리에 적재하지 않고, 네트워크를 통해 들어오는 데이터를 청크 단위로 지연 평가하여 클라이언트 사이드에서 페이지네이션을 처리할 수 있도록 방어 로직을 구축했습니다.

하지만 페이지네이션 UX를 구현하기 위해서는 사용자에게 "전체 페이지 수" 를 제공해야만 했습니다. 현재의 API 구조에서는 전체 데이터의 개수를 파악하기 위해 결국 스트림이 종료될 때까지 데이터를 끝까지 순회하며 카운트 해야 하는 한계가 존재했습니다. 이로 인해 메모리 오버플로우 문제는 방어해 냈지만, 불필요한 네트워크 대역폭 소비와 CPU 연산을 완전히 차단하지는 못했습니다.

## AI 활용 범위

### 1. 디자인 시스템 및 UI 블루프린트 프로토타이핑

Stitch Url : <https://stitch.withgoogle.com/projects/9766716684876052105>

복잡한 다단계 폼을 설계할 때, 뷰 계층의 시각적인 구조가 먼저 정의되어야만 그에 맞는 상태 관리 및 데이터 흐름을 설계할 수 있다고 판단했습니다. 이를 위해 초기 단계에서 구체적인 요구사항과 레이아웃 지시사항을 Stitch 에 주입하여 전체적인 UI와 디자인 시스템의 블루프린트를 빠르게 스캐폴딩 했습니다. 뷰 계층의 기초 공사 시간을 단축함으로써, 저는 핵심 도메인 로직을 분리하고 예외 상황을 방어하는 아키텍처 설계에 리소스를 집중할 수 있었습니다.

### 2. 테스트 자동화 및 대용량 데모 데이터 스크립트 작성

테스트 환경을 구축하고 모의 데이터를 생성하는 과정에서 발생하는 반복적이고 보일러플레이트적인 코드 작성에 AI를 적극 활용했습니다. 여기서 중요한 점은 AI에게 설계 자체를 위임한 것이 아니라는 것입니다. 제가 먼저 요구사항을 깊이 분석하여 극단적인 엣지 케이스와 검증해야 할 행동 시나리오를 줄글 형태로 치밀하게 기획했습니다. 이후 이 '인간이 작성한 시나리오'를 AI에게 제공하여 Vitest 단위 테스트와 Playwright E2E 테스트 코드로 번역(Translate)하게끔 통제했습니다. 동일한 방식으로 수만 건의 데모 데이터를 생성하는 스크립트 또한 AI의 도움을 받아 빠르게 구축하여, 극한의 렌더링 환경에서의 안정성 테스트를 효율적으로 수행할 수 있었습니다.

### 3. 코드 작성

실질적인 코드 구현 단계에서는 가장 작은 단위부터 시작하여 점진적으로 조립해 나가는Bottom-up 방식을 취했습니다. 처음부터 거대한 페이지나 복잡한 기능을 통째로 AI에게 맡기기보다는, 우선 공통으로 쓰일 도메인 타입과 Zod 스키마를 직접 선언하여 데이터 구조의 명확한 기준을 세웠습니다. 이후 개별 UI 컴포넌트처럼 작은 단위를 구현할 때는 테스트 코드를 먼저 작성하게 하고, 이를 통과하는 코드를 생성하도록 유도했습니다. 생성된 코드들은 코드 리뷰를 하듯 부족한 부분을 수정하며 다듬었고, 이렇게 검증을 마친 작은 컴포넌트들을 모아 다단계 라우팅과 전역 상태 파이프라인이라는 커다란 구조로 차근차근 조립해 나가며 프로젝트를 완성했습니다.

### 4. AI-에이전트 협업 및 아키텍처 제어 방법론

프로젝트 진행 과정에서 AI 도구를 활용할 때, 무작위 코드 생성으로 발생할 수 있는 품질 파편화를 방지하기 위해 몇 가지 협업 원칙을 설정하여 적용했습니다. 첫째, 프로젝트 아키텍처 규칙(수직 아키텍처, 캡슐화 규칙)과 디자인 시스템 토큰을 사전에 명시하여 AI가 정해진 설계 틀 안에서 코드를 생성하도록 유도했습니다. 둘째, 대규모 리팩토링이나 복잡한 요구사항을 한 번에 요청하지 않고 단위 기능별로 분할하여 점진적으로 코드를 작성하고 검증해 나갔습니다. 마지막으로, 생성된 코드의 부작용을 예방하기 위해 린트 검사와 단위/E2E 테스트 실행 결과를 피드백으로 활용하여 지속적으로 코드를 보정하고 보완했습니다. 이러한 방식을 통해 코드의 일관성을 유지하면서 개발 과정을 효율적으로 관리할 수 있었습니다.
